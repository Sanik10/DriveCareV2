# Границы денежного контура DriveCare


Дата: 2026-01-20


## 1) Цель и принцип
**Цель:** в проекте DriveCare единственный денежный поток, в котором DriveCare является получателем оплаты — это подписка автосервиса на платформу (SaaS). Все остальные модули CRM не создают и не проводят денежный оборот платформы.


Ключевой принцип: *разделяем контуры*:
- **Platform Billing (деньги DriveCare)** — подписка/тарифы.
- **External Payment Integrations (деньги автосервиса и его клиента)** — опциональные интеграции, где DriveCare не является стороной расчётов.


## 2) Денежный контур DriveCare (subscription billing)
### 2.1. Модули и файлы
Относятся к деньгам DriveCare и требуют усиленного аудита/проверок:
- `apps/backend/src/modules/subscriptions/subscription-billing/**`
- `apps/backend/src/modules/tariffs/**`
- `apps/backend/src/modules/subscriptions/services/subscription-limits.service.ts`


Сущности БД (денежный контур подписки):
- `apps/backend/src/database/entities/subscription.entity.ts`
- `apps/backend/src/database/entities/tariff.entity.ts`
- `apps/backend/src/database/entities/subscription-payment-log.entity.ts`
- `apps/backend/src/database/entities/subscription-consent.entity.ts`
- `apps/backend/src/database/entities/subscription-compliance-log.entity.ts`


### 2.2. API пути
Единственные endpoints, где пользователь (автосервис) платит деньги DriveCare:
- `POST /api/v1/subscription-billing` — создать подписку (PENDING)
- `POST /api/v1/subscription-billing/payment` — инициировать/захватить оплату
- `POST /api/v1/subscription-billing/webhooks/:provider` — вебхуки провайдеров
- `DELETE /api/v1/subscription-billing/:id` — отмена подписки


### 2.3. Обязательные гарантии (P0)
**Идемпотентность:**
- `Idempotency-Key` должен работать не только на уровне PSP, но и на уровне БД.
- Повторные запросы не должны создавать: (а) дубликаты подписок PENDING, (б) дубликаты логов оплаты.


**Вебхуки:**
- Обязателен дедуп на уровне бизнес-логики (не только sha256(rawBody)).
- Действия `activateSubscription` и `cancelSubscription` должны быть идемпотентными.


**Аудит и PII:**
- Для subscription-billing фиксируем: кто, когда, что оплатил/отменил, с каким idempotencyKey, correlationId.
- Политика хранения IP/UserAgent: сроки хранения + запрет логировать секреты/Authorization.


**Запрет bypass:**
- Запрещён скрытый bypass подписки (например «временно выключим guard»).
- Для тестирования используются только контролируемые механизмы: промокод/триал (раздел 4).


## 3) Внешние платежи автосервиса (не деньги DriveCare)
Это *опциональный* интеграционный контур. Он влияет на статусы/учёт, но не должен превращать DriveCare в сторону расчётов.


### 3.1. Модули и API (интеграции)
- `apps/backend/src/modules/payments/**`
- `apps/backend/src/modules/payment-methods/**`
- `apps/backend/src/modules/invoices/**` (если хранит статусы оплат как факт)
- сущности: `payment.entity.ts`, `payment-method.entity.ts`, `invoice.entity.ts`


Webhook endpoints внешних платежей (отдельно от subscription-billing):
- `POST /api/v1/payments/webhooks/yookassa`
- `POST /api/v1/payments/webhooks/tinkoff`


### 3.2. Принцип изоляции
- Разные URL для webhooks (не смешивать с subscription-billing).
- Разные ключи/секреты/настройки.
- Никаких вызовов `SubscriptionBillingService/*` из модулей payments/invoices.
- Модуль `payments` не имеет права читать/менять сущности подписки: `Subscription`, `SubscriptionPaymentLog`.


## 4) Политика тестирования без bypass
**Запрещено:** скрытый bypass подписки (guard отключён) как постоянный dev-приём.


**Разрешено (рекомендовано):** тестовая подписка через промокоды/триал.


### 4.1. Механизм: промокод/триал (план)
Добавить сущность (пример): `PromoCode` со следующими полями:
- `code` (уникальный)
- `tariffId`
- `durationDays` (например 14/30)
- `maxRedemptions`, `redeemedCount`
- `expiresAt`, `isActive`


API (ограничить ролью `platform_admin/superadmin`):
- `POST /api/v1/subscription-billing/promo/redeem` — активирует подписку без оплаты, ставит `paymentMethod='trial'` или `paymentMethod='promo'`, пишет audit + compliance log.


### 4.2. Жёсткий запрет bypass в production
В `apps/backend/src/config/validation.schema.ts` добавить:
- `BILLING_DEV_BYPASS` (boolean, default false) и правило: **в production всегда false**.
- либо вообще не вводить bypass, а вводить только promo/trial.


## 5) Ближайшие технические задачи (конкретно)
1) Реализовать идемпотентность в `createPendingSubscription` и `createOrCapturePayment` с использованием Redis keys из `BILLING_CONSTANTS.REDIS_KEYS.*` + TTL.
2) Исправить дедуп вебхуков: перейти с sha256(rawBody) на ключ дедупа `provider + paymentId + status` (и/или eventId), + предусмотреть поведение при недоступном Redis.
3) Сделать `activateSubscription` транзакционным и идемпотентным: повтор не должен плодить аудит и не должен падать при конкурирующих апдейтах (учесть уникальность active-подписки на компанию).
4) Документировать модель безопасности YooKassa webhook (IP allowlist обязателен в production) и проверить, что raw-body действительно используется только на webhook путях.
5) Унифицировать конфиг TTL дедупа вебхуков: использовать один параметр окружения (например `WEBHOOK_IDEMPOTENCY_TTL_SEC`) и не читать его из несовпадающих ключей.
