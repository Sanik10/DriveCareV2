Часть A. Подтверждено (реальные проблемы и сделанные фиксы)
- Auth/Сессии/Redis
  - Подтверждено: lastUsedAt не обновлялся по каждому авторизованному запросу → онлайн/активность были неточными.
  - Исправлено: JwtStrategy вызывает sessionService.updateSessionActivity() для каждого валидного запроса.
  - Подтверждено: deviceId зависел от IP, из-за чего плодились “новые устройства”. Исправлено: deviceId строится только на основе UA и пользователя (IP — лишь во fingerprint).
- Payment Methods (способы оплаты)
  - Подтверждено: 401 на странице методов оплаты из‑за того, что фронт доставал токен из localStorage и ходил fetch-ами в обход общего клиента. Исправлено: переложено на apiRequest, авто‑refresh по cookie RT.
  - Подтверждено: 400 при создании — валидация DTO “type” через IsEnum (на массив) и числа/булевые без transform. Исправлено: заменено на IsIn и добавлен Type(()=>Number/Boolean).
  - Подтверждено: Плашка “Требует настройки” горела у офлайн‑методов. Исправлено: маппер бэка помечает офлайн‑методы isConfigured=true (без интеграции).
  - Подтверждено: UX создателя/редактора — добавлена клиентская валидация в соответствии с константами бэка, поля интеграции показываются только для online‑типов.
  - Подтверждено: отвечает более человекочитаемой ошибкой 400 (EnhancedValidationPipe + GlobalExceptionFilter собирают сообщение и errors[] в DEV).
- Ошибки “сохранение не срабатывает” и “требует настройки”
  - Подтверждено: “Сохранение” срывало из-за несоответствия формата/payload (строки вместо чисел, пустой gatewayType для online в некоторых кейсах). Сейчас клиент нормализует данные; офлайн‑методы больше не требуют интеграции; online — требуют gatewayType, только если вы его указали (иначе поле вообще не отправляем).

Часть B. Явные пробелы (видно по дереву проекта и наличию/отсутствию страниц)
- Inventory/Склад (фронт не закрыт, бэк есть)

    - /dashboard/suppliers (список/карточка/аналитика/рейтинг),

- Service history (история обслуживания)
  - Бэкенд: modules/service-history есть.
  - Фронт: нет страницы (/dashboard/service-history или вкладки у автомобиля/клиента).
- Audit logs (журнал аудита)
  - Бэкенд: common/audit/audit.service.ts и audit-log.entity.ts.
  - Фронт: нет /dashboard/audit (фильтры по типу, пользователю, компании, кореляции).
- Company settings (центральные настройки компании)
  - Бэкенд: косвенно поддерживается (реквизиты в entities), но централизованной формы нет.
  - Фронт: нет /dashboard/settings/company (реквизиты, логотипы/печати, нумерация, НДС, часовой пояс, шаблоны печати/писем).
- Public Pay page (оплата счета без логина)
  - Бэкенд: payments/webhooks готовы, есть feature/pay-invoice на фронте.
  - Фронт: отсутствует публичный роут вида /pay/:token (R/O статус + переход/результат), чтобы клиент мог оплатить счет без авторизации.
- Управление интеграциями платформы (subscription-billing)
  - Бэкенд: subscription-billing есть, вебхуки для YooKassa/Tinkoff есть.
  - Фронт: нет явной страницы “Интеграции платформы” (где настраиваются ключи для оплаты тарифов DriveCare) — сейчас смешение возможно с “payment-methods” компаний, что неверно.
- Роли/права — нет UI тонкой настройки
  - Сейчас работают роли, но нет UI “пермишнов”, если потребуется гибкий RBAC (переключатели на уровне действий).
- Gateway list endpoint
  - Сейчас front вводит gatewayType текстом. Нет /payment-methods/gateways (список из констант), чтобы дать селект и исключить опечатки.
- Work Schedules vs Appointments — UI сформирован через “Записи” (канбан/календарь), но…
  - Вы используете доску “Записи” в стиле тайм-слотов (как календарь iOS). Это классно, но:
    - Нет явного UI для самих “рабочих расписаний” и “исключений” (отпуска, перерывы) с накладыванием на сетку, статусы смен.
    - Нет визуализации capacity (вместимость) и “heat map” занятости.
    - Нет “snap to schedule” (привязка к слотам смен) и отображения конфликтов/ограничений из work-schedules при драг&дроп.

Часть D. Предложения по доработкам (пошаговый план)
0) Быстрые добивки (1–2 дня)
- Payment gateways селект:
  - Бэк: добавить GET /payment-methods/gateways (из PAYMENT_METHODS_CONSTANTS.SUPPORTED_GATEWAYS).
  - Фронт: заменить текстовый ввод на select; сохранить “Другое” (manual) как фолбэк опцией.
- Public Pay page:
  - Фронт: /pay/:token (SSR рендер статуса, кнопка “Оплатить”, результат).
  - Бэк: endpoint выдачи PaymentIntent по токену инвойса (если уже есть — задокументировать и прикрутить).
- Company settings (минимальный MVP):
  - Общие реквизиты, НДС флаги, валюта/TZ, логотип.
  - Нужна 1 страница с tabs.

1) Inventory (основной блок, 1–1.5 недели на MVP)
- /dashboard/inventory:
  - Витрина: остатки, резервы, дефицит, быстрые действия “Провести приход/расход”, посленедельная динамика.
- /dashboard/inventory/movements:
  - Список фильтрованный (дата/тип/контрагент/деталь), форма создания движения (приход/расход/перемещение), скан ШК.
- /dashboard/suppliers:
  - Список, карточка, аналитика (средние сроки, цена, рейтинг), массовый импорт (если требуется).
- /dashboard/inventory/alerts:
  - Список критичных/низких запасов, “гасить/закреплять”, настройки порогов (перенос из InventoryAlerts).

2) Work schedules/appointments (улучшения UX, 3–5 дней на “ощутимое”)
- Включить визуализацию исключений (отпуска/перерывы) поверх доски “Записи”.
- Авто-привязка к слотам смен (snap), подсветка конфликтов.
- Переключатели Day/Week/Mechanic (ресурсный вид), быстрые фильтры.
- Capacity/hints: показывать занятость и “доступный объём” на слот.

3) Audit logs (2–3 дня)
- /dashboard/security/audit:
  - Фильтры: тип события, статус, пользователь, компания, корреляция (request-id).
  - Экспорт CSV.

4) Service history (3–4 дня)
- Вкладка у автомобиля/клиента “История обслуживания”:
  - Список работ и запчастей по нарядам, интервалы, файлы/документы.
  - Экспорт (PDF/CSV).

5) Интеграции платформы (subscription-billing) (2–3 дня)
- /platform/integrations:
  - YooKassa/Tinkoff ключи для оплаты тарифа DriveCare (не компании-клиента).
  - Тест соединения, лог последних вебхуков, health.

Часть F. Acceptance criteria (чтобы мы одинаково понимали “готово”)
- Payment-methods:
  - Офлайн‑методы не помечаются “Требует настройки”.
  - Для online‑методов “Настроен” → только когда gatewayType задан; клиент и бэк валидируют согласованно.
  - Успешное создание/редактирование без ложных 400/401, человекочитаемые ошибки.
- Inventory:
  - Витрина: видны остатки, дефицит, и можно быстро провести приход/расход.
  - Движения: фильтры, создание с валидациями, история, скан (если нужно).
  - Поставщики: CRUD + базовая аналитика (срок/цена/рейтинг).
  - Alerts: список + настройка порогов/каналов.
- Work schedules/appointments:
  - Запись не может быть размещена в закрытом/перекрытом слоте; есть подсказки capacity; драг&дроп “с привязкой”.
- Public pay:
  - По ссылке без логина клиент видит статус счета и может инициировать оплату; страница состояния после провайдера.

Часть G. Риски/заметки
- Валидация в DEV стала шумнее (подробные ошибки) — в PROD защищено и не раскрывает лишнего.
- Для будущих платежных провайдеров (СБП и т.п.) желательно развести “тип метода” vs “шлюз” на уровне модели (сейчас мы компенсировали в маппере/фронте, но схемой всё ещё смешано).
- Для печатных форм лучше сразу выбрать подход: серверный PDF (e.g. PDFKit) или клиентский (html-to-pdf) — влияет на доставку/качествo.
