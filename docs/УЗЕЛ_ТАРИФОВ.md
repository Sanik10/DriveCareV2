Окей, фиксирую всё в одном месте — актуальная “карта местности” и пошаговый план, чтобы можно было продолжать работу даже если чат пропадёт.

DriveCare — Узел тарифов/подписки: актуальное состояние и план завершения

1) Где мы сейчас
- Архитектура: Monorepo (Turborepo), backend на NestJS + TypeORM + Redis + Schedulers, frontend на Next.js (App Router, Tailwind). Redis работает, сиды в dev создают супер‑админа, cron’ы активны.
- Бэкенд (после последних правок):
  - Поток подписки ведём через /subscription-billing (вариант B).
  - Добавлен billingPeriod ('monthly'|'yearly') в CreateBillingSubscriptionDto и в сущность Subscription.
  - Сумма теперь считается на сервере из тарифов priceMonthly/priceYearly (ProcessPaymentDto.amount опционален и игнорируется).
  - ФЗ‑блоки активны:
    - ФЗ‑242: проверяем SERVER_REGION/LOCATION/DATA_PROCESSING_LOCATION == RU (иначе блокируем).
    - ФЗ‑152: требуем pdnConsentGiven и consumerRightsAcknowledged.
    - ФЗ‑161: MIR — логируем факт проверки, фиксируем mirCardUsed.
  - Вебхуки: /subscription-billing/webhooks/:provider (raw-body + дедуп в Redis), по успеху — автоактивация подписки, по refund/cancel — автокэнсел.
  - Идемпотентность: поддержка X-Idempotency-Key в create/payment; дедуп вебхуков (sha256 сырого тела).
  - YooKassa: return_url = FRONTEND_URL/dashboard/payments/result?context=subscription.
- Фронтенд:
  - Тарифный каталог/деталь/витрина есть.
  - Базовая обвязка API (core.ts) — безопасное подключение и идемпотентность.
  - Модуль payments — сейчас ориентирован на оплаты инвойсов (/payments). Для подписок нужно отдельный клиент /subscription-billing и доработка /dashboard/payments/result под context=subscription.

2) Какие контракты считаем “истиной”
- Создание подписки (единый шаг, без автопродления):
  - POST /subscription-billing
  - Тело: { tariffId, billingPeriod ('monthly'|'yearly'), pdnConsentGiven: true, consumerRightsAcknowledged: true, paymentMethod?, startDate? }
  - Ответ: BillingSubscriptionResponseDto (включая billingPeriod и daysUntilExpiration).
- Инициация оплаты:
  - POST /subscription-billing/payment
  - Тело: { subscriptionId, gatewayProvider?, paymentMethod?, metadata? } — amount на фронте не считаем, сервер посчитает сам.
  - Ответ: PaymentStatusResponseDto с paymentId, status, provider, redirectUrl?.
- Получение активной подписки:
  - GET /subscription-billing/active → BillingSubscriptionResponseDto | null.
- Отмена:
  - DELETE /subscription-billing/:id → { success: true } (без автопродления).

3) Что нужно настроить для запуска с YooKassa
- ENV backend:
  - YOOKASSA_SHOP_ID=<ваш_shop_id>
  - YOOKASSA_SECRET_KEY=<ваш_secret_key>
  - FRONTEND_URL=https://ваш-фронтенд-домен (без слеша в конце)
  - SERVER_REGION=RU
  - SERVER_LOCATION=Russia
  - DATA_PROCESSING_LOCATION=RU
  - DEFAULT_PAYMENT_PROVIDER=yookassa (опционально)
  - Если планируете Tinkoff: TINKOFF_TERMINAL_KEY, TINKOFF_PASSWORD
- В YooKassa:
  - Return URL: https://ваш-фронтенд-домен/dashboard/payments/result (мы добавляем ?context=subscription сами).
  - Webhook (по желанию): POST https://ваш-api-домен/api/v1/subscription-billing/webhooks/yookassa
- CORS: добавить домен фронта в whitelist backend’а.
- ДБ: добавлено поле billingPeriod — если миграций нет, просто пересоздайте БД (docker-compose down -v → up).

4) End‑to‑end флоу (как должно работать)
- Авторизованный пользователь:
  1) Нажимает “Подключить” на тарифе → модалка выбора периода (месяц/год), согласий (2 чекбокса) и метода оплаты (card/mir/sbp/wallet/bank_transfer).
  2) POST /subscription-billing с billingPeriod и согласиями → подписка в PENDING, endDate рассчитан на бэке.
  3) POST /subscription-billing/payment (subscriptionId + paymentMethod) → ответ с redirectUrl и paymentId.
  4) Перед редиректом фронт кладёт paymentId в sessionStorage ('lastPaymentId'), затем уходит на redirectUrl.
  5) Возврат на /dashboard/payments/result?context=subscription → страница показывает статус и ссылку “в /dashboard/billing”.
     - Для подписки лучше не тянуть /payments/:id (это модуль инвойсов), а показывать “ожидание” и параллельно опрашивать GET /subscription-billing/active (пока статус не станет ACTIVE).
- Неавторизованный:
  - “Приобрести” → /auth/register?tariffId=... → после регистрации CTA “Завершить покупку” (открыть ту же модалку).

7) Тест‑план (минимальный)
- Авторизованный сценарий:
  - Месячный план: успех → статус ACTIVE → daysUntilExpiration ≈ 30.
  - Годовой план: успех → daysUntilExpiration ≈ 365.
  - Отмена → статус CANCELED.
- Неавторизованный:
  - CTA ведёт на /auth/register?tariffId=...
- Ошибки:
  - ФЗ‑242: подставить неверные SERVER_*, убедиться что create подписки блокируется.
  - Без согласий — 400.
  - Неподдерживаемый paymentMethod — 400.
- Вебхуки:
  - Имитация webhook “succeeded” → подписка активируется.
  - “refunded/cancelled” → подписка отменяется.

8) Безопасность и соответствие ФЗ РФ — на что обратить внимание
- ФЗ‑242: в проде выставить ENV в RU, сервер должен физически работать на инфраструктуре с локализацией данных (логика на бэке проверяет).
- ФЗ‑152: на UI без чекбоксов недоступна кнопка “Оплатить”; на бэке вход без согласий блокируется; логи комплаенса пишутся.
- ФЗ‑161: включите метод ‘mir’ в UI; в логах помечаем mirCardUsed; при необходимости отдельный сценарий MIR‑карт.
- Идемпотентность: для create/payment в UI использовать generateIdempotencyKey() и отправлять в X-Idempotency-Key.
- Сумма платежа — всегда на сервере; любые значения с фронта игнорируются.
- 54‑ФЗ (чеки): сейчас в интеграции YooKassa payload Receipt не заполняется (MVP). Для боевого PCI/54‑ФЗ потребуется донастройка чеков через провайдера или интеграция с ОФД — это вынесено в отдельную задачу.

9) Риски/ограничения сейчас
- Страница /dashboard/payments/result для контекста “subscription” пока не использует paymentId → она полагается на активацию подписки вебхуком/переходом и проверяет /subscription-billing/active. Это ок для MVP.
- Если webhook временно недоступен — пользователь может увидеть “обрабатывается”; при обновлении страницы или через несколько секунд активная подписка подтянется (за счёт фоновой активации).
- Разделение модулей “инвойсные платежи” vs “подписки” на фронте пока не доведено — мы разведём клиенты (payments.ts vs subscription-billing.ts) и логику result/page.

11) Ответы на частые вопросы
- Нужно ли ещё что-то, кроме замены ссылок для YooKassa? Да:
  - Настроить ENV (YOOKASSA_*, FRONTEND_URL, SERVER_*=RU), CORS, и (по желанию) webhook URL.
  - Пересоздать БД (или мигрировать), потому что добавлен столбец billingPeriod.
- Можно ли оставить Tinkoff “наготове”? Да, провайдер и gateway есть; основной поток ведём через YooKassa.
- Что с модулем payments на фронте? Для подписок — не используем. Он остаётся для инвойсов. Мы разведём логику в result/page.tsx по параметру context.
