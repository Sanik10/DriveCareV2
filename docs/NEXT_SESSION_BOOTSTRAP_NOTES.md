AI Path-Blocks Workflow (Backend/Frontend)

Цель: получать от ИИ валидные правки в формате path‑blocks, которые скрипт применяет автоматически. Сначала — аудит (без кода), потом — правки. Если точного контента файлов нет — запрос “NEED FILES”.

Режимы

1) Audit (без кода)
- Обязательно запросить файлы, а потом идти по этапам ниже. Угадывать содержимое файлов строго запрещено. Работать только по факту!
- Никаких файлов/патчей. Только текстовый отчёт.
- Покрыть:
  - РФ-комплаенс: 152‑ФЗ, 242‑ФЗ, 402‑ФЗ, 54‑ФЗ, 161‑ФЗ, ст. 54.1 НК РФ, ПП РФ №1119, приказы ФСТЭК (№21, №239 и смежные), СКЗИ/крипто по необходимости, 187‑ФЗ (КИИ — если применимо), PCI DSS (если соприкасаемся с картами).
  - Безопасность: аутентификация/авторизация (RBAC), входная валидация, XSS/SQLi/CSRF, безопасные заголовки и cookies, протоколирование/аудит, ретеншн/удаление, секреты, шифрование.
  - Качество кода: архитектура, модули/слои, DTO/валидация, транзакции/идемпотентность, наблюдаемость, производительность.
- Вывести:
  - Приоритетный план изменений (P0/P1/P2) с мотивацией и ожидаемым эффектом.
  - Список затронутых файлов/модулей.
  - Зависимости (миграции БД, конфиги, ключи).
  - Риски и quick wins.

2) Edits (path‑blocks)
Миграции можно не делать! Ты можешь просто заменить код в сущности! Я могу спокойно удалить БД и создать заново!
- Если нет точного содержимого файлов → сначала верни блок “NEED FILES”.
- Если точные версии есть → присылай только path‑blocks (один блок = один файл, всегда полный валидный контент).

Шаблон запроса точных версий файлов (если они нужны)
```
NEED FILES (нужны точные текущие версии файлов для корректных правок):
- apps/backend/src/.../file-a.ts
- apps/backend/src/.../file-b.ts
Причина: правки в формате path‑blocks требуют полного, актуального содержимого, иначе велика вероятность ошибок.
```

Формат path‑blocks (обязателен)

- Один файл — один блок. Полный валидный контент файла.
- В каждом блоке обязательно:
  1) HTML‑комментарий с путём (для скрипта)
  2) Тот же путь первой строкой комментария внутри файла (если язык поддерживает комментарии)
- Пути от корня репозитория:
  - apps/backend/src/...
  - apps/frontend/src/...
  - .env.example, turbo.json и т.д.
- Действия: replace|delete|append|move (replace по умолчанию). Для move обязательно from.

Синтаксис блока
<!-- path: относительный/путь/к/файлу[, action: delete|replace|append|move, from: старый/путь] -->
```lang
// path: относительный/путь/к/файлу
<полное содержимое файла>
```

- lang: ts, js, tsx, json, yaml, md, sh и т.д.
- Если формат без комментариев (JSON/YAML/ENV) — внутренний комментарий не вставлять.

Примеры

1) Замена/создание файла
<!-- path: apps/backend/src/modules/users/users.service.ts -->
```ts
// path: apps/backend/src/modules/users/users.service.ts
import { Injectable } from '@nestjs/common';
import { UsersRepository } from './services/users-data.service';

@Injectable()
export class UsersService {
  constructor(private readonly repo: UsersRepository) {}
  // ...
}
```

2) Удаление файла
<!-- path: apps/backend/src/modules/old/obsolete.service.ts, action: delete -->
```ts
// path: apps/backend/src/modules/old/obsolete.service.ts
```

3) Добавление строк в конец
<!-- path: .env.example, action: append -->
```dotenv
# path: .env.example
NEW_FEATURE_FLAG=true
```

4) Перемещение
<!-- path: apps/backend/src/modules/foo/bar.service.ts, action: move, from: apps/backend/src/modules/old/bar.service.ts -->
```ts
// path: apps/backend/src/modules/foo/bar.service.ts
// обновлённый контент (если нужен)
```

Правила отправки ответа
- Только path‑blocks. Никаких diff/patch.
- В каждый изменённый файл — полный валидный контент (не фрагменты).
- Без дублей одного и того же файла; присылай финальную версию один раз.
- UTF‑8 без BOM, переводы строк LF, без невидимых символов; пустая строка в конце файла.
- JSON/YAML/ENV — строго валидный синтаксис.

Подсказка по комментариям внутри файла
- TS/JS/TSX/JSX/Go/C#: // path: apps/backend/src/...
- CSS/SCSS/Less: /* path: apps/backend/src/... */
- HTML/XML/SVG/MD: <!-- path: apps/backend/src/... -->
- Shell/YAML/ENV/INI/TOML/Python/Ruby/SQL: # или -- в SQL
- Для форматов без комментариев (JSON/YAML/ENV) — внутренний комментарий не использовать.

Расширенный чек‑лист по РФ (комплаенс, безопасность, качество)

Персональные данные — 152‑ФЗ
- Роли: оператор ПДн, порученные лица (процессоры) — договоры поручения с требованиями защиты ПДн.
- Уведомление Роскомнадзора (если не подпадаете под исключения).
- Политика обработки ПДн (публично); фиксация согласий субъектов (версия текста, дата/время, канал).
- Права субъектов: доступ/исправление/удаление/ограничение — реализовать процессы/эндпоинты и логирование исполнения.
- Спецкатегории/биометрия — обрабатывать только на законных основаниях, с усиленными мерами.
- Кросс‑граничная передача — правовые основания, перечень стран, проверка адекватности защиты.
- Минимизация, ограничение сроков хранения; процедуры удаления/анонимизации; учёт операций обработки.
- Инциденты ПДн — регламент реагирования и уведомления уполномоченных органов/субъектов в установленные сроки.

Требования защиты — ПП РФ №1119 + приказы ФСТЭК (№21, №239 и др.)
- Классификация ИСПДн и определение уровня защищенности.
- Модель угроз и нарушителя; план организационно‑технических мер.
- Меры: управление доступом, аудит событий, антивирус/EDR, межсетевые экраны, сегментация, шифрование каналов/данных, резервирование, контроль целостности.
- Применение сертифицированных СЗИ (ФСТЭК/ФСБ) — при необходимости по уровню защищенности.
- Актуализация угроз; оценка соответствия/аттестация при необходимости.

Локализация ПДн — 242‑ФЗ
- Первичная запись, систематизация и хранение ПДн граждан РФ — на территории РФ.
- Если используете облака — дата‑центры в РФ, договор с условиями защиты, контроль репликации.

Бухучёт — 402‑ФЗ
- Первичные учётные документы должны соответствовать требованиям закона (реквизиты, неизменяемость).
- Сроки хранения учётной документации — не менее 5 лет (если иные сроки не установлены).
- ЭДО: обеспечивать целостность, подлинность, отслеживаемость изменений.

Расчёты/чеки — 54‑ФЗ (ККТ), платёжные сервисы — 161‑ФЗ, налоги — ст. 54.1 НК РФ
- 54‑ФЗ: при расчётах с физлицами обязателен чек ККТ, передача через ОФД и отправка покупателю (email/SMS).
- Проверить, кто выбивает чек (вы или агрегатор/банк по договору): теги, НДС, тип расчёта, возвраты/корректировки.
- Хранить связку платеж ↔ чек (ID заказа, FN/FD/FPD и пр.).
- 161‑ФЗ: безопасность переводов, информирование клиента, соблюдение правил платёжной системы.
- 54.1 НК РФ: отсутствие схем “дробления”, фиктивных контрагентов; достоверность первички и корректная фискализация.

КИИ (если применимо) — 187‑ФЗ
- Идентификация значимых объектов, категорирование, выполнение требований защиты.

PCI DSS (если соприкасаетесь с реквизитами карт)
- Предпочтительно не хранить PAN/CVV — используйте токенизацию провайдера (YooKassa/Tinkoff и др.).
- Если обрабатываете — область соответствия, сегментация, шифрование, процедуры комплаенса.

Практика безопасной разработки и эксплуатации
- Валидация и санитайз в DTO; white‑list для сортировок/фильтров.
- Безопасные заголовки (helmet), HSTS, корректный CORS; httpOnly/secure cookies; защита от CSRF.
- Аутентификация/авторизация: JWT/2FA, роли/права на уровне контроллеров и сервисов; принцип наименьших привилегий.
- Криптография: argon2/bcrypt для паролей; crypto.randomBytes для токенов; запрет устаревших алгоритмов (MD5/SHA1).
- Секреты: только ENV/Secret Manager; маскирование в логах; ротация ключей.
- Логи/аудит: без ПДн в “сыром” виде; маскирование; синхронизация времени (NTP).
- Наблюдаемость: метрики, трассировки, алерты.
- Бэкапы: регулярность, шифрование, тест восстановления.
- DevSecOps: линты/формат, SAST/DAST/Dependency Audit, секрет‑сканеры в CI, проверка лицензий.
- Миграции БД: атомарны, с откатами; миграции отдельно от бизнес‑кода.

Мини‑памятка по документации
- Политика ПДн (публично), реестр обработок, согласия субъектов (артефакты/логи).
- Договоры поручения с процессорами; распределение ответственности за ПДн.
- Модель угроз/нарушителя; уровень защищенности; план мер; перечень СЗИ.
- Регламенты доступа, реагирования на инциденты, уничтожения данных/носителей; журналы аудита.
- По 54‑ФЗ: регламенты фискализации/возвратов, хранение фискальных реквизитов.

Процесс: как работать с этим промптом
- Шаг 1. Audit: ИИ делает анализ и предлагает план (без кода).
- Шаг 2. NEED FILES: если для правок нужен точный контент — ИИ запрашивает файлы.
- Шаг 3. Edits: ИИ присылает только path‑blocks с полным содержимым файлов и обязательными комментариями пути.
- Шаг 4. Применение: запускаем скрипт с --prefer-blocks/по умолчанию.
- Шаг 5. Проверка: линтеры/тесты/сборка; при необходимости — следующий короткий цикл Audit → Edits.
