# DriveCare V2

## Краткое описание

DriveCare — это мультиарендная платформа для управления небольшими автосервисами. Система закрывает ключевые процессы сервиса: учёт клиентов и автомобилей, записи и заказы‑наряды, услуги и запчасти, счета и онлайн‑оплату (YooKassa), а также подписку на тарифы самой платформы. Проект реализован как monorepo (NestJS backend + Next.js frontend) с PostgreSQL и Redis, с упором на безопасность, аудит и удобство дальнейшего развития.

---

## Основные возможности

### Для автосервиса

- **Клиенты и автомобили (CRM)**
  - база клиентов с контактами и согласиями на обработку ПДн;
  - учёт автомобилей, пробега, истории обращений;
  - экспорт/анонимизация клиентов, retention‑policy.

- **Записи и расписание**
  - записи на обслуживание (appointments) с выбором клиента/авто/механика/услуг;
  - Smart‑Schedule: рекомендации по времени с учётом загрузки;
  - проверка доступности (check‑availability), трекинг статуса записей;
  - рабочие графики и исключения (backend: work‑schedules, на UI частично учтено).

- **Заказы‑наряды и работы**
  - заказы с услугами и запчастями;
  - статусы заказов и работ, назначение исполнителей;
  - пересчёт итогов, связка с инвойсами и оплатами.

- **Счета и платежи**
  - выставление счетов (invoices) вручную и из заказа;
  - статусы, отмена, отчёты по просрочкам;
  - онлайн‑оплата через YooKassa: инициация платежа, вебхуки, фискальные чеки у провайдера;
  - возвраты (refund) с идемпотентностью, виджет баланса и базовая аналитика.

- **Платёжные методы**
  - хранение способов оплаты сервиса (онлайн/офлайн);
  - проверка интеграции онлайн‑методов, расчёт комиссии;
  - скрытие чувствительных данных (API‑ключей) на уровне UI и API.

### Для платформы DriveCare

- **Мультиарендность**
  - одна «компания» = один автосервис (или небольшая сеть);
  - внутри компании — пользователи с ролями и правами;
  - жёсткое разделение данных по companyId.

- **Тарифы и подписки**
  - сущность Tariff с лимитами, ценами (ежемесячно/ежегодно) и набором фич;
  - маркетинговые флаги: recommended, badge, tags, highlight, shelf_position;
  - подписки компаний на тарифы (Subscriptions) с ограничением 1 активная подписка на компанию;
  - публичная витрина тарифов (каталог/сравнение) без внутренних метрик;
  - backoffice‑интерфейс с метриками (activeSubscribers/totalSubscribers) и расширенными фильтрами.

- **Безопасность и аудит**
  - ролевая модель (owner, admin, manager, mechanic и др.), guards по ролям и владению;
  - 2FA, управление сессиями устройств, logout‑all;
  - журнал аудита действий (audit‑log);
  - унифицированная валидация и человекочитаемые ошибки в DEV;
  - stop‑лист API‑эндпоинтов, недоступных из UI (webhooks, system, интеграции).

## Архитектура репозитория

Monorepo на Node.js:

```text
.
├── apps
│   ├── backend        # NestJS API и бизнес-логика
│   └── frontend       # Next.js (App Router) и UI
├── docs               # Живая документация по архитектуре и модулям
├── docker-compose.yml # Postgres + Redis
├── package.json       # Общие dev-зависимости и скрипты (Turborepo и пр.)
├── turbo.json         # Конфигурация monorepo (если используется Turborepo)
└── ...
```

### Backend (`apps/backend`)

- **Стек**
  - NestJS 10 (REST API, DI, модули);
  - TypeScript 5;
  - TypeORM 0.3 + PostgreSQL 16;
  - Redis 7 (ioredis) для сессий, идемпотентности и вспомогательных задач;
  - Nest Schedule/Throttler/Swagger/Config.

- **Структура**
  - `src/app.module.ts` — корневой модуль;
  - `src/config/*` — конфигурация (env, схемы, валидация);
  - `src/database/*` — data-source, entities, migrations, seeds;
  - `src/common/*` — кросс‑срезы: audit, guards, pipes, interceptors, redis;
  - `src/modules/*` — доменные модули (auth, customers, vehicles, orders, invoices, payments, subscriptions, tariffs, inventory и др.);
  - `src/cli/*` — вспомогательные скрипты (создание супер‑админа, сиды).

### Frontend (`apps/frontend`)

- **Стек**
  - Next.js (App Router);
  - TypeScript;
  - TailwindCSS (и близкий к shadcn/ui набор компонентов в `components/ui`);
  - FSD‑подход с алиасами: `@app/*`, `@shared/*`, `@entities/*`, `@features/*`, `@widgets/*`, `@providers/*`, `@store/*`.

- **Структура**
  - `app/(auth)` — логин/регистрация/инвайты;
  - `app/dashboard/*` — рабочий кабинет автосервиса:
    - `customers`, `vehicles`, `orders`, `services`, `parts`,
    - `invoices`, `payments`, `payment-methods`,
    - `appointments`, `security` и др.;
  - `app/platform/*` — интерфейсы платформы (каталог ТС, тарифы DriveCare);
  - `app/tariffs/*` — публичный каталог тарифов/страницы сравнения;
  - `components/*` — UI и доменные компоненты;
  - `lib/api/*` — API‑клиенты поверх единого `apiRequest`;
  - `lib/types/*` — DTO/типы для всех доменов.

## Backend: доменные модули и особенности

### Аутентификация и безопасность

- **Auth & Sessions**
  - Локальный логин (email/логин + пароль) + 2FA на базе `otplib`;
  - JWT‑авторизация (access + refresh), хранение RT в cookie;
  - Сессии устройств в БД + Redis:
    - `lastUsedAt` обновляется для каждого валидного запроса (статус «онлайн» корректен);
    - `deviceId` строится по UA+пользователь (IP влияет только на fingerprint, не плодит устройства);
  - Guards:
    - `jwt-auth.guard`, `local-auth.guard`;
    - guards на роли (`roles.guard`), владение компанией (`company-ownership.guard`), комбинированный `auth-with-ownership.guard`.

- **Роли и права**
  - Сущности `Role`, `Permission`, `User`, `Company`;
  - Иерархия ролей и системные роли (superadmin, platform_admin, owner, admin, manager и др.);
  - Декораторы `@Roles()`, `@Resource()` и прочие для декларативного описания доступа.

- **Валидация и ошибки**
  - `EnhancedValidationPipe` — расширенная валидация DTO:
    - нормализует типы (через `class-transformer` / `Type(() => Number/Boolean)`),
    - отдаёт человекочитаемые ошибки и массив `errors[]` в DEV;
  - `GlobalExceptionFilter` — унифицированный JSON‑ответ, маскировка чувствительных деталей в PROD.

- **Аудит и безопасность**
  - `common/audit/audit.service.ts` + `audit-log.entity.ts`:
    - журналирует ключевые действия (создание/изменение/удаление, входы, опасные операции);
  - Interceptors:
    - `audit-logging.interceptor.ts`,
    - `security-headers.interceptor.ts` (Helmet‑подобные заголовки, защита от XSS/Clickjacking).

### Компании и пользователи

- **Companies / Users**
  - Onboarding компании, редактирование реквизитов (backend готов; централизованный экран настроек компании в UI — в планах);
  - Управление пользователями компании: создание, инвайты, смена ролей/статусов, профиль;
  - Согласия (`user-consent`), сессии (`user-session`), инвайты (`user-invite`).

### Клиенты, история и ПДн

- **Customers**
  - CRUD клиентов, поиск, фильтры;
  - Согласия на обработку данных, отзыв согласия;
  - Экспорт данных, анонимизация, retention‑политики (scheduler).

- **Service History**
  - Backend‑модуль для истории обслуживания (`service-history`):
    - хранение выполненных работ и установленных запчастей;
    - привязка к авто и клиенту;
  - UI‑вкладка «история обслуживания» для автомобиля/к��иента — запланирована.

### Автомобили и каталог

- **Vehicles**
  - Автомобили клиентов, пробег, статусы;
  - Обновление пробега, привязка к клиенту и истории обслуживания.

- **Vehicles Catalogue**
  - Глобальный справочник марок/моделей/типов ТС;
  - Импорт внешних справочников;
  - На UI используется для селектов; CRUD каталога — только для платформенных ролей/бэкофиса.

### Заказы, расписания и записи

- **Orders**
  - Заказы‑наряды с услугами/запчастями:
    - добавление/удаление позиций, пересчёт итогов;
    - изменения статуса заказа;
    - назначение исполнителя;
  - Управление статусами и назначением по услугам заказа (JSON‑контракты в соответствии с backend API);
  - Связка с инвойсами и оплатами.

- **Work Schedules**
  - Рабочие графики и исключения (отпуска, выходные, перерывы);
  - Расчёт вместимости (capacity) и оптимизация — на уровне backend;
  - На UI пока используется опосредованно через логику Smart‑Schedule (планируются более наглядные расписания и «heat map» загрузки).

- **Appointments**
  - Записи клиентов:
    - листинг с фильтрами (статус/приоритет/даты/поиск);
    - создание записи (диалог с асинхронными селектами клиентов/авто/механиков/услуг);
    - check‑availability и Smart‑Schedule (подбор слота);
    - детальная карточка с действиями (подтвердить/отменить/перенести/завершить/оценить);
    - трекинг статуса;
  - Планируется углубление интеграции с Work‑Schedules (Smart‑Schedule v2, явная визуализация графиков и исключений).

### Счета, платежи и интеграции

- **Invoices**
  - Счета (инвойсы) с привязкой к заказам и платежам:
    - создание вручную и из заказа;
    - статусы, отмена, мягкое удаление;
    - отчёты: дашборд статистики, отчёт по просроченным инвойсам.

- **Payments**
  - Платежи (в т.ч. онлайн) в связке с инвойсами:
    - инициация онлайн‑платежа через YooKassa: `POST /payments/online/init`;
    - возвраты (refund) с `X-Idempotency-Key`;
    - баланс компании и базовая аналитика;
  - Вебхуки:
    - `/payments/webhooks/yookassa` — только для провайдера (ACL по IP, верификация статуса у провайдера, идемпотентность);
    - UI‑клиенты не имеют доступа к `/payments/webhooks/*` и `/payments/system/*` (stop‑лист).

- **Payment Methods**
  - Типы методов: онлайн (YooKassa и др.) и офлайн;
  - DTO и валидация:
    - `EnhancedValidationPipe` + корректная типизация (числа/булевы через `Type()`),
    - более человекочитаемые 400‑ошибки в DEV;
  - Офлайн‑методы помечаются как `isConfigured=true` без интеграции (исправлено: ранее UI показывал «требует настройки»);
  - Online‑методы требуют корректного `gatewayType`; ошибки формата/payload нормализованы.

### Тарифы и подписки

- **Tariffs**
  - Публичные эндпоинты (без метрик):  
    `GET /tariffs`, `/tariffs/active`, `/tariffs/popular`, `/tariffs/compare`, `/tariffs/:id`;
  - Админский эндпоинт с метриками:  
    `GET /tariffs/admin` (только для superadmin/platform_admin);
  - Полный CRUD:
    - `POST /tariffs`, `PATCH /tariffs/:id`, `PATCH /tariffs/:id/status`, `DELETE /tariffs/:id`;
    - запрет удаления активных/исторических тарифов;
  - Метрики:
    - `activeSubscribers`, `totalSubscribers` по distinct companyId и статусам/датам подписки;
  - Бизнес‑правила:
    - годовая цена ≤ monthly×12, скидка ≥1%;
    - уникальное имя (case‑insensitive);
  - Маркетинговые флаги в `features.jsonb`:
    - `recommended`, `badge`, `tags[]`, `highlight`, `shelf_position`;
    - нормализация и валидация на backend.

- **Subscriptions**
  - Подписки компаний на тарифы:
    - статусы: ACTIVE/PENDING/SUSPENDED/CANCELED/EXPIRED/INACTIVE;
    - уникальное ограничение `uniq_active_subscription_per_company`;
  - Используются для расчёта метрик тарифов и управления доступом к функционалу;
  - UI для управления подпиской компании (billing dashboard) — в разработке.

## Frontend: ключевые идеи

### Стек и структура

- Next.js (App Router) + TypeScript + TailwindCSS;
- Компонентный набор `components/ui` (кнопки, формы, диалоги, skeleton и др.);
- FSD‑подход: разделение на `entities`, `features`, `widgets`, `pages`, `providers`, `store`.

### Единый API‑клиент

- `lib/api/core.ts`:
  - `apiRequest` / `apiRequestRaw` — единая точка входа для HTTP;
  - stop‑лист запрещённых эндпоинтов (webhooks/system/integrations/hard-delete);
  - автоматическое обновление access‑токена по 401 (refresh по cookie RT, retry запроса);
  - централизованный `buildApiUrl`, передача JSON через `init.json`;
  - генерация `X-Idempotency-Key` для write‑операций, где поддержано на backend.

### Основные экраны

- `(auth)`:
  - логин, регистрация компании, регистрация по инвайту, успех регистрации;
  - 2FA и управление устройствами — в разделе `dashboard/security`.

- `/dashboard/*`:
  - **customers** — список/деталь/создание;
  - **vehicles** — список/деталь/создание, обновление пробега;
  - **services** — список/редактирование/создание;
  - **parts** — список/редактирование/создание, поиск;
  - **orders** — список/создание/деталь, kanban‑представление, диалоги добавления услуг/запчастей;
  - **invoices** — список/создание (вручную и из заказа)/деталь, статусы, отчёты;
  - **payments** — список/деталь, возврат (refund), баланс;
  - **payment-methods** — список/создание/редактирование, тоггл статуса, проверка интеграции и расчёт комиссии;
  - **appointments** — список/создание/деталь, Smart‑Schedule, действия по записи;
  - **security** — 2FA, сессии устройств, logout‑all.

- `/platform/*`:
  - **catalogue** — управление глобальным каталогом ТС (для платформенных ролей);
  - **tariffs** — backoffice‑интерфейс тарифов с метриками и маркетинговыми флагами.

- `/tariffs/*`:
  - публичный каталог тарифов и сравнение (read‑only, без внутренних метрик).

### Политика безопасности фронтенда

- UI обращается только к «UI‑safe» ручкам (customers, orders, invoices, payments без webhooks/system, appointments и др.);
- Стоп‑лист на уровне `apiRequest` блокирует:
  - `/payments/webhooks/*`, `/payments/system/*`;
  - `/subscription-billing/webhooks/*`;
  - `/stock-movements/integrations/*`;
  - hard‑delete PII/первичной бухгалтерии;
- Метрики тарифов отображаются только в backoffice (`/tariffs/admin`), публичные страницы получают ответы без метрик;
- Действия, недоступные по роли, скрываются в UI (не полагаемся только на 403).

## Запуск и локальная разработка

### Предварительные требования

- Node.js (рекомендуется 20.x);
- npm / pnpm / yarn (в примерах — `npm`);
- Docker и Docker Compose (для PostgreSQL и Redis).

### 1. Клонирование и установка зависимостей

```bash
git clone <url-репозитория> drivecare
cd drivecare

# Установить зависимости монорепо
npm install
```

При необходимости можно отдельно установить зависимости в приложениях:

```bash
cd apps/backend
npm install

cd ../frontend
npm install
```

### 2. Настройка окружения

Создайте `.env` (или используйте систему переменных окружения) с минимумом для `docker-compose.yml`:

```env
POSTGRES_USERNAME=drivecare
POSTGRES_PASSWORD=drivecare_password
POSTGRES_DATABASE=drivecare_db

REDIS_PASSWORD=some_secure_password
```

Также нужно настроить переменные для backend (имена и формат смотрите в `apps/backend/src/config/configuration.ts`), например:

- параметры подключения к БД (host, port, username, password, database);
- параметры Redis (host, port, password);
- секреты JWT/refresh токенов;
- параметры YooKassa (shopId, secretKey, callback URL) и других интеграций;
- базовый URL фронтенда/бэкенда.

### 3. Поднять инфраструктуру (Postgres + Redis)

Из корня репозитория:

```bash
docker compose up -d postgres redis
```

Docker Compose:

- поднимет PostgreSQL 16 на `localhost:5433`;
- поднимет Redis 7 на `localhost:6380` с паролем `REDIS_PASSWORD`.

### 4. Миграции и сиды БД

```bash
cd apps/backend

# Применить миграции
npm run db:migrate

# (Опционально) выполнить сиды для базовых данных
npm run seeds:run

# (Опционально) создать супер-админа
npm run db:create-admin
```

### 5. Запуск backend

В `apps/backend`:

```bash
cd apps/backend

# Режим разработки
npm run start:dev

# или
npm run start
```

По умолчанию NestJS поднимает HTTP‑сервер на порту, указанном в конфигурации (часто 3000 или 4000). Актуальный порт можно уточнить в `main.ts`/конфигах.

### 6. Запуск frontend

В `apps/frontend` (конкретные скрипты смотрите в `apps/frontend/package.json`, как правило это `dev`/`build`/`start`):

```bash
cd apps/frontend

# Режим разработки
npm run dev
```

После запуска frontend будет доступен на порту, настроенном в Next.js (обычно 3000).
